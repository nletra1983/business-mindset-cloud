# Research: Расшифровка голосовых сообщений

Решения ниже основаны на `features/voice-messages/business-logic.md`, текущем Telegram-контуре и конституции 1.2.0.

## Граница входа: только voice-сообщение с микрофона

- Decision: В обработку входят только Telegram `voice` сообщения; `audio` и `video_note` не считаются входом этой истории.
- Rationale: Это зафиксировано в бизнес-логике и удерживает срез узким.
- Alternatives considered: обрабатывать `audio` и `video_note` так же, как `voice` — отвергнуто как расширение границы истории.

## Точка интеграции в коде

- Decision: Добавить voice-ветку в `telegram_poll._dispatch` до `handle_text(...)`, чтобы после распознавания text проходил существующую логику.
- Rationale: Так переиспользуется уже покрытый правилами path для шага хода, профиля и dedup update.
- Alternatives considered: отдельный voice-runner модуль и отдельный pipeline — отвергнуто, лишняя развилка и риск рассинхронизации с text-flow.

## Поведение для неподдерживаемых моделей

- Decision: Для моделей без подтверждённого voice-path сразу отвечать `Эта модель не разбирает голос.` и не двигать шаг.
- Rationale: Бизнес-логика явно фиксирует такое поведение; голос не должен случайно менять состояние.
- Alternatives considered: fallback на другую модель для распознавания — отвергнуто, это меняет выбранную модельную логику и границу среза.

## Поведение при пустом результате распознавания

- Decision: Если распознавание не вернуло текст, отвечать `Голос не разобран.` и не передавать событие в text-flow.
- Rationale: Нужен recoverable path без побочных эффектов на run/profile state.
- Alternatives considered: передавать пустую строку в `handle_text` — отвергнуто, это активирует побочные сценарии (например blank-topic) и смещает семантику ошибки распознавания.

## Отображение распознанного текста

- Decision: При успешном распознавании сначала отправлять пользователю распознанный текст отдельным сообщением без подписи, затем обрабатывать его как обычный ввод человека.
- Rationale: Это прямое требование бизнес-логики и делает преобразование прозрачным для пользователя.
- Alternatives considered: скрытая обработка без показа распознанного текста — отвергнуто, теряется прозрачность.

## Хранение данных

- Decision: Сохранять только текстовую реплику в существующий `utterance`; аудио-байты не сохранять.
- Rationale: Продуктовая запись остаётся текстовой; хранение audio не требуется и увеличивает риски.
- Alternatives considered: сохранять бинарный audio payload в БД/файл — отвергнуто как выход за границу и ненужное усложнение.
