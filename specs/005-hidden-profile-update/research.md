# Research: Обновлять скрытый файл профиля по результату задания

Решения ниже основаны на `features/account-settings/business-logic.md`, `ProductArtifacts/skill-profile-slice.md`, `features/business-idea-from-news/FeatureArtifacts/user-profile-mindset.md` и конституции 1.2.0.

## Источник данных для обновления hidden-профиля

- Decision: Обновлять hidden-профиль только из структурированных наблюдений результата упражнения (характеристика, сигнал, свидетельство, run id), а не из свободного текста финального ответа.
- Rationale: Правила статусов должны быть детерминированными и тестируемыми; парсинг prose-ответа модели нестабилен.
- Alternatives considered: извлекать сигналы из текста `what_worked/what_weak` — отвергнуто из-за хрупкости и риска ложных обновлений.

## Граница для короткого разбора (smoke)

- Decision: Для короткого разбора разрешить обновлять только `spotting` согласно продуктовой границе, остальные пять характеристик не трогать.
- Rationale: В бизнес-логике явно зафиксировано, что короткий разбор «событие и масштаб» может менять только «замечать возможность».
- Alternatives considered: обновлять все характеристики по косвенным признакам — отвергнуто как выход за границу истории и переинтерпретация данных.

## Правила слияния статусов между ходами

- Decision: Вынести merge-правила в единый доменный слой: первое наблюдение меняет `не наблюдалось`, повтор того же знака во втором завершённом ходе ставит `устойчиво`, противоречие ставит `неравномерно` и сохраняет оба свидетельства.
- Rationale: Эти правила используются повторно и должны быть консистентны между упражнениями.
- Alternatives considered: хранить только последнее состояние и стирать историю — отвергнуто, теряется причина перехода и невозможно объяснить `неравномерно`.

## Идемпотентность повторной доставки результата

- Decision: Ввести dedup по `run_id + characteristic_id` при записи свидетельств и обновлении статуса.
- Rationale: Канальный контур может доставлять событие повторно; без dedup статус и история будут «раздуваться».
- Alternatives considered: надеяться на единичную доставку — отвергнуто, противоречит инварианту устойчивости к повторной доставке.

## Выбор поля «сейчас тренировать»

- Decision: После каждого обновления выбирать ровно одну характеристику в приоритете: `слабо` → `неравномерно` → `не наблюдалось`, ограничивая выбор теми характеристиками, которые затрагивает ближайшее упражнение.
- Rationale: Это соответствует артефакту профиля и не превращает поле в «седьмой навык».
- Alternatives considered: случайный выбор или фиксированный порядок без учёта статуса — отвергнуто как менее полезное для тренировочного фокуса.

## Приватность hidden-профиля

- Decision: Hidden-статусы и внутренние ids не выводить в user-visible ответах и не изменять прямой правкой `информация о себе`.
- Rationale: Бизнес-логика разделяет два файла о человеке и запрещает смешение.
- Alternatives considered: единый профиль с фильтрацией на выдаче — отвергнуто, повышает риск утечки и случайной перезаписи.
