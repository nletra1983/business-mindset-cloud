# Мобильные приложения

Линза включается для своего клиента на устройстве. Сайт и бот в чужом мессенджере её не включают: у них другой контейнер и другие ограничения площадки, их достаточно назвать на контексте.

Класс клиента фиксируется только здесь. Имя библиотеки, номера версий и файл установки сюда не копировать: это скилл `mobile-app-architect`.

## Какой клиент

Выбирай по ограничениям сценария, не по моде.

| Вариант | Бери, когда |
|---|---|
| Адаптивный веб | Сценарий редкий, магазины и офлайн не нужны, push не обязателен |
| Два нативных клиента | Нужны последние возможности платформы, разный UX, на устройстве тяжёлая графика или своя модель |
| Общая логика и два нативных интерфейса | Логика, сеть, кэш и правила синхронизации одни, а интерфейс и способности ОС разные |
| Один общий интерфейс | Интерфейс общий, команда одна, сценарий не упирается в платформенные исключения |

Для продукта с нетривиальной логикой на устройстве и двумя магазинами в текущей сборке стартовая гипотеза — общая логика и два нативных интерфейса, если нет команды, которая уже целиком живёт в одном общем интерфейсе. Нетривиальная логика здесь — та, что обязана жить на устройстве. Если правила исполняет сервер, клиент ведёт общий диалог, а пишет один человек, бери один общий интерфейс, даже когда оба магазина есть только в горизонте. Гипотезу сверь с людьми, которые будут писать клиент. Не вводи три клиента.

Для этого репозитория класс уже выбран: один общий интерфейс. Причина совпадает с правилом выше: правила хода на сервере, офлайн, датчики, пуши и модель на телефоне не нужны, первая сборка — файл автору на Android, магазины позже, пишет один человек с Windows.

Сервер остаётся владельцем правил, за которые платят или по которым спорят. Клиент может повторять проверку ради отклика, но не становится единственным местом, где правило исполняется.

## Офлайн

Офлайн-первый режим закладывай, только если главное действие обязано завершаться без сети. Тогда локальная база — источник правды для экрана, а сеть — фоновая синхронизация.

Минимальный шов такого режима: запись сначала на устройстве, очередь исходящих изменений с ключом идемпотентности, сервер умеет принять повтор. Если офлайн не нужен, не рисуй очередь синхронизации «на всякий случай». Кэш чтения — обычная часть клиента, отдельного архитектурного решения он не требует.

## Доверие на устройстве

- Секреты сессии — в аппаратном хранилище платформы, не в обычных настройках и не в встроенной базе в открытом виде.
- Вход в свои учётные записи предпочитай через passkey с проверкой утверждения на сервере. Если пользователи корпоративные, вход идёт через их поставщика идентичности, passkey его не подменяет.
- Данные на устройстве шифруй, если при потере устройства утечёт то, что в сценарии вреда названо серьёзным.
- Закрепление сертификата и обфускация не заменяют нормальную авторизацию на сервере. На верхнем уровне их не расписывай.

## Магазины и оплата

Политика магазина может запретить выбранную оплату внутри приложения. Если бизнес-модель берёт деньги с мобильного пользователя, это развилка до выбора контейнера оплаты: оплата провайдером по правилам площадки или сценарий, который площадка не считает цифровой покупкой. Не обещай обход комиссии схемой глубоких ссылок.

Фоновые обновления кода ограничены площадкой. Не закладывай произвольную подмену клиента вне механизма магазина.

## Модель на устройстве

На устройстве считай, если сценарий должен жить без сети, задержка облака ломает действие или данные нельзя отправлять в чужую модель. В облаке считай, если качество доступно только у большой модели или вес модели неприемлем для установки.

Системная модель платформы предпочтительнее модели, вшитой в поставку: её обновляет ОС и она не раздувает сборку. Доступность на устройстве бывает разной, поэтому у сценария нужен запасной путь: облако, упрощённое правило или честный отказ. Общий код оркестрирует шаг, исполнение остаётся платформенным.

На схеме отдельный AI-контейнер на телефоне не рисуй, пока модель не является отдельной поставляемой частью со своим циклом обновления. Иначе это модуль внутри мобильного контейнера.

## Что видно на C4

Мобильное приложение — один контейнер на платформу или один контейнер общего интерфейса, в соответствии с классом выше. Для этого репозитория это один контейнер общего интерфейса. В ответственности напиши, что хранится на устройстве. Push, если он есть, — внешняя система площадки, а не свой сервер очередей, пока свой брокер не потребовался по другой причине.
