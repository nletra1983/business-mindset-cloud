# /publish

Одна команда «обновить везде» для этого репозитория. Текст после команды — что пометить в карте (номера/имена историй и новый статус). Пример: `/publish мобильное №2 №3 №4 №5 done`.

## Что входит

| Куда | Как |
|---|---|
| Git | коммит связанных правок + `feature-map.md` |
| Сервер (бот, `/app/v1`) | `git push origin main` → GitHub Actions `Deploy bot` (агент на Selectel по SSH **не** заходит) |
| Телефон | если менялись `mobile/` или скрипт сборки — собрать APK локально |
| Карта | `features/feature-map.md` — статусы историй/фичи |

Не трогать без явной просьбы: DNS, nginx, certbot, секреты, удаление файлов, force-push.

## Статусы

Цепочка: `draft` → `ready-for-speckit` → `specified` → `planned` → `in-impl` → `done` | `parked`.

Правила:

1. Статусы брать из текста команды, если человек их назвал.
2. Если не назвал — коротко предложить таблицу (история → было → станет) по факту этой сессии и незакоммиченных правок. **Не менять карту**, пока человек не подтвердит («да», «как предлагаешь», или пришлёт свою таблицу).
3. Не ставить `done`, если на сервере/в APK ещё нет того, что история обещает человеку. Для серверного фикса без UI телефона — `done` у серверной истории ок; у Flutter-истории — только если APK уже отражает срез или человек явно сказал «done».
4. Секреты (`.env`, `key.properties`, ключи) в коммит не класть.

## Порядок шагов

1. Прочитать `features/feature-map.md`. Сверить с `git status` / diff, что реально менялось.
2. Согласовать или применить статусы (см. выше). Записать карту.
3. Закоммитить: код среза + `features/feature-map.md` (+ связанные docs/skills этого среза, если они в diff и человек не запретил). Сообщение коммита — зачем, на языке репозитория.
4. `git push origin main`.
5. Проверить Actions: `gh run list --workflow "Deploy bot" --limit 1` (или открыть URL run). Дождаться успеха или сразу сказать, что деплой пошёл и как проверить. При падении — кратко причина, без «тихого» успеха.
6. APK:
   - если в коммите/сессии менялось `mobile/` (или человек написал «и APK») — собрать:
     ```powershell
     $env:CHANNEL_BASE_URL = "https://get-business-idea.ru"
     powershell -ExecutionPolicy Bypass -File "mobile\tool\build_author_apk.ps1"
     ```
   - путь к файлу: `mobile\build\app\outputs\flutter-apk\app-release.apk`
   - если Flutter/SDK нет — сказать, что сервер обновлён, APK собрать на ПК с Flutter.
   - если `mobile/` не менялось — APK не собирать, явно написать «телефон не трогал».
7. В чат — короткое саммари (шаблон ниже). Язык: простой русский, полные пути, без жаргона без расшифровки.

## Флаги в тексте команды

| Фраза | Смысл |
|---|---|
| `без пуша` / `только коммит` | коммит + карта, без `git push` |
| `без APK` | не собирать телефон |
| `без карты` | не менять `feature-map.md` |
| `только карта` | только статусы, без коммита кода (если код уже в main — ок; иначе спросить) |

## Саммари человеку

```
Карта: <что сменили или «без изменений»>
Коммит: <hash> <одна строка>
Push: main → origin (деплой Actions: ок / идёт / ссылка / ошибка)
APK: <путь> или «не собирал»
Дальше: <одна фраза — например «поставь новый APK» или «через 1–2 мин проверь вход»>
```

## Связь с другими командами

- Не заменяет `/po-new-feature`, Spec Kit и `/check-ready-to-speckit`.
- После зелёного implement можно сразу `/publish … done` вместо отдельного «коммить и пуш».
- Правило репо: push в `main` по этой команде считается **явной просьбой** человека опубликовать.
